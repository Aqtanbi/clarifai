# ClarifAI

ИИ-агент статической проверки документа с требованиями по **ISO/IEC/IEEE 29148:2018** (п. 5.2.5, 5.2.6) и **IEEE Std 830-1998** (п. 4.3).
Читает документ (PDF, DOCX, MD, TXT, HTML), выделяет отдельные требования, проверяет каждое требование и набор целиком,
**доказывает противоречия расчётом** на исполняемой модели требований и выпускает отчёт на русском в **Markdown, HTML и PDF**.

Три способа запуска: **CLI** (основной, одна команда), **веб-сайт** (Vercel) и **MCP-сервер** (Claude Desktop, Cursor, VS Code).

---

## Быстрый старт (Windows)

```bat
git clone https://github.com/Aqtanbi/adamizer.git
cd adamizer
py -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
```

Откройте `.env` и вставьте ключ в `GEMINI_API_KEY` (см. «Как получить ключ»). Затем запустите проверку:

```bat
python main.py docs\requirements.pdf -o reports\report.md
```

Отчёт появится в папке `reports\`:

| Файл | Что это |
|---|---|
| `report.md` | отчёт в Markdown |
| `report.pdf` | тот же отчёт в PDF (кириллица, таблицы) |
| `report.html` | самодостаточная HTML-версия |
| `report.json` | машиночитаемый результат (требования, находки, итог) |
| `report_interactive.html` | **интерактивный отчёт**: документ с подсвеченными местами дефектов и список находок рядом; открывается в браузере без интернета |

Linux/macOS: `python3 -m venv .venv && source .venv/bin/activate`, далее те же команды (`cp .env.example .env`).

### Как получить ключ LLM
1. Откройте https://aistudio.google.com/apikey и войдите с Google-аккаунтом.
2. Нажмите **Create API key** и скопируйте ключ.
3. Вставьте его в `.env`: `GEMINI_API_KEY=...`. Бесплатного тарифа достаточно.
4. Модель задаётся в `GEMINI_MODEL`. **Команда использует `gemini-3.5-flash-lite`** (Google AI Studio, бесплатный тариф): на ней сформирован сдаваемый отчёт, она же стоит по умолчанию. Модели 2.5 для новых ключей отключены. Список доступных моделей: `python main.py --list-models`. Модель, на которой выполнен прогон, всегда записывается в паспорт отчёта.

Другие провайдеры: `LLM_PROVIDER=openai` с любым OpenAI-совместимым API (OpenAI, OpenRouter, Groq, локальная Ollama через `OPENAI_BASE_URL=http://localhost:11434/v1`).

### Параметры CLI

```
python main.py <документ> [-o reports/report.md] [--no-pdf] [--no-html] [--full] [--no-sim] [--no-critic] [--lint] [--no-cache] [--model NAME]
```

Ответы модели кэшируются в `.cache/`: повторный прогон того же документа воспроизводим и не тратит лимиты. Для чистого прогона используйте `--no-cache`.

## Как работает агент

```
документ ─► 0. Профиль документа (LLM: тип, предметная область, структура, нумерация →
               чек-лист рисков именно для этого документа; подставляется во все этапы ниже)
         ─► 1. Парсинг ─► 2. Нарезка ─► 3. Проверка каждого ─► 4. Проверка набора ─► 5. Проверка расчётом
              (PDF/DOCX/MD,   (LLM: R-01…,   требования (LLM,       (LLM: противоречия,     (LLM пишет модель правил
               страницы,       ID документа,  9 критериев 29148      пропуски, термины,      на Python → песочница →
               разделы,        цитата)        пакетами)              трассируемость)         сценарии и границы)
               номера строк)
         ─► 6. (по флагу --lint) детерминированные правила без LLM
         ─► 7. Grounding: каждая цитата программно сверяется с текстом документа
         ─► 8. Рецензент (LLM: убирает ложные находки и дубли, калибрует серьёзность, выносит итог)
         ─► 9. Отчёт: MD + HTML + PDF + JSON
```

Что отличает агента:

- **Ни одной цитаты без проверки.** Каждая цитата ищется в тексте документа, с нормализацией регистра, кавычек, тире и разметки. Неточная цитата заменяется на точный текст документа. Если цитата не найдена, находка исключается. Защита от подмены смысла: при нечётком совпадении нельзя потерять отрицание («не») или изменить число. В отчёте выводится статистика, например «цитат подтверждено 47/47».
- **Проверка расчётом.** Агент переводит правила в исполняемую модель и прогоняет критерии приёмки, граничные значения и сценарии на стыке правил. Если ожидаемое документом расходится с вычисленным, противоречие доказано. Если сценарий проходит только при альтернативном прочтении правила, доказана неоднозначность. Код модели приложен к отчёту. Он выполняется в песочнице: только разрешённые модули стандартной библиотеки, проверка AST, отдельный процесс, таймаут, без сети и ключей.
- **Подстраивается под любой документ.** Жёстких правил под конкретный документ нет: агент сам определяет тип документа (ТЗ, SRS, user stories, API-спецификация…), схему нумерации и предметную область и составляет чек-лист рисков под него. Чек-лист виден в отчёте. Проверка расчётом запускается, только если в документе есть формализуемые правила. Детерминированный линтер выключен по умолчанию (`--lint`).
- **Рецензент.** Независимый проход отсеивает ложные срабатывания. Отброшенные находки с причиной видны в приложении B.
- **Каждая находка готова к работе:** критерий с пунктом стандарта, серьёзность, цитата и место (раздел, страница, строка), проблема, рекомендация, **готовая исправленная формулировка** и вопрос владельцу продукта.
- **Интерактивный отчёт «документ и находки».** Слева документ, в котором места дефектов подсвечены цветом серьёзности, справа находки с фильтрами. Клик по подсветке открывает находку, клик по находке прокручивает документ к цитате; у противоречия подсвечиваются оба места. Внутри находки — «было → стало» и вопрос владельцу. Доступен на сайте (вкладка) и файлом `report_interactive.html` из CLI.
- **Матрицы:** «требование × критерий» и трассируемость «требование → критерии приёмки».

### Состав отчёта

По умолчанию формируется **краткий отчёт** (около 5–8 страниц): на первой странице итог, главные дефекты и что исправить первым. Подробные карточки выводятся только для критичных и существенных находок, мелкие замечания идут одной строкой в таблице. Полный отчёт со всеми карточками, матрицей трассируемости и приложениями включается флагом `--full` (на сайте — галочкой «Полный отчёт»). Оба варианта содержат все разделы, обязательные по ТЗ.

1. Паспорт прогона: документ, дата, модель, версия агента (git-тег или коммит), токены, время.
2. Нарезка: «ID в отчёте — ID в документе — тип — краткая формулировка — цитата и место».
3. Проверка каждого требования: матрица критериев и карточки нарушений.
4. Проверка всего набора: по критериям 29148 п. 5.2.6 и IEEE 830 п. 4.3, трассируемость, неопределённые термины.
5. Проверка расчётом: варианты прочтения, сценарии, расхождения.
6. Сводка: число требований и нарушений, разбивка по критериям, критичные дефекты (непроверяемые, противоречивые, неполные).
7. Итог: можно ли начинать разработку и тестирование, что исправить в первую очередь.

Приложения: A — критерии; B — контроль качества (grounding, отброшенные находки); C — код модели.

## Веб-сайт (Vercel)

Локально:
```bat
uvicorn webapp:app --reload
```
Откройте http://127.0.0.1:8000. Там загрузка документа, прогресс по этапам, просмотр отчёта и скачивание PDF/MD/HTML.

Развёртывание:
1. Импортируйте репозиторий на https://vercel.com/new. Конфигурация уже в `vercel.json`, точка входа `api/index.py`.
2. **Settings → Environment Variables:** `GEMINI_API_KEY` и `GEMINI_MODEL`. Рекомендуется `ACCESS_CODE`, чтобы чужие не тратили ваш ключ (пользователь со своим ключом код не вводит), и `MCP_TOKEN` для защиты `/mcp`.
3. Deploy. Версия агента в паспорте берётся из `VERCEL_GIT_COMMIT_SHA`.

Ограничения Vercel: функция работает до 300 с (`maxDuration`), тело запроса до 4.5 МБ. Полный прогон обычно занимает 1–4 минуты. Если не укладывается, отключите симуляцию галочкой или уменьшите `BATCH_SIZE`.

## MCP-сервер

Инструменты: `validate_requirements`, `extract_requirements`, `verify_quote` (без LLM), `list_criteria`; локально ещё `validate_requirements_file`, который пишет отчёт на диск.

**Claude Desktop (Windows)**: `%APPDATA%\Claude\claude_desktop_config.json`
```json
{
  "mcpServers": {
    "clarifai": {
      "command": "C:\\path\\to\\adamizer\\.venv\\Scripts\\python.exe",
      "args": ["C:\\path\\to\\adamizer\\mcp_server.py"],
      "env": { "GEMINI_API_KEY": "ваш_ключ" }
    }
  }
}
```

**Удалённо (сайт на Vercel)**: Streamable HTTP по адресу `https://<проект>.vercel.app/mcp/`, заголовок `Authorization: Bearer <MCP_TOKEN>`, если токен задан.

## Тесты и оценка качества

```bat
python tests\test_pipeline.py
python eval\run_eval.py reports\report.json eval\gold.json
```

`test_pipeline.py` — офлайн-тест конвейера на моке LLM (без ключа). `run_eval.py` считает полноту (recall) находок по эталонному списку дефектов, который команда составляет вручную для своего документа (формат описан в начале скрипта). Это инструмент разработки для сравнения версий промптов и моделей: эталон в репозиторий не входит и агенту не передаётся.

