# ClarifAI — ИИ-ревьюер требований, который доказывает свои выводы

**ClarifAI за 1–3 минуты проверяет документ с требованиями по ISO/IEC/IEEE 29148 и IEEE 830 и находит противоречия, пробелы и неоднозначности до начала разработки.** Каждое нарушение привязано к дословной цитате, противоречия подтверждаются расчётом, у каждого дефекта есть готовая исправленная формулировка.

### 🔗 Попробовать сразу: **https://clarifai-rv5l.onrender.com**
Код доступа: **`qwerty123`**. Загрузите PDF/DOCX/MD и нажмите «Проверить».
<sub>Бесплатный сервер засыпает после 15 минут простоя, первое открытие занимает около минуты.</sub>

| | |
|---|---|
| **Находит главное** | На выданном документе находит все ключевые противоречия, например «Ф-2 считает месяц по дате совершения, а критерий приёмки №2 ждёт февраль» и «Ф-3 разрешает один push в месяц, а Ф-4 требует ещё один». Критичных дефектов найдено 4–5 из 5. |
| **Полнота** | 56–71% на эталоне из 34 дефектов, который команда разметила вручную (3 прогона на бесплатной `gemini-3.5-flash-lite`). |
| **Без галлюцинаций в цитатах** | 100% цитат в отчёте программно сверены с текстом документа. Находки с невоспроизводимой цитатой в отчёт не попадают. |
| **Скорость и цена** | 1–3 минуты на документ вместо часов ручного ревью. Работает на бесплатном тарифе Gemini. |

## Чем ClarifAI отличается

1. **Противоречия доказываются, а не утверждаются.** ИИ пишет исполняемую модель правил документа и прогоняет на ней каждый критерий приёмки, граничные значения и сценарии на стыке правил. Если документ ожидает одно, а по его же правилам получается другое, противоречие доказано вычислением. Код выполняется в песочнице: только безопасные модули, отдельный процесс, таймаут, без сети и ключей.
2. **ИИ обязан показать работу.** Модель пересчитывает каждый критерий приёмки по тексту требований и задаёт к каждому требованию 3–6 «вопросов разработчика» с отметкой, отвечает ли на них документ. Находки собираются из этих расчётов и неотвеченных вопросов автоматически. Ответ «всё хорошо» без проверки невозможен.
3. **Ни одной выдуманной цитаты.** Каждая цитата ищется в документе. Неточная заменяется точным текстом, но только если не потеряно «не» и не изменилось число. Выдуманные цитаты отбрасываются.
4. **Подстраивается под любой документ.** Сначала ИИ определяет тип документа (ТЗ, SRS, user stories, спецификация API…), предметную область и нумерацию. Затем составляет чек-лист рисков именно для этого документа. Ничего не зашито под выданный пример.
5. **Отчёт, с которым можно работать.** У каждого дефекта есть критерий с пунктом стандарта, место в документе, «было → стало» и вопрос владельцу продукта. Интерактивный режим «документ и находки» подсвечивает в тексте места дефектов, а клик по находке показывает её место.
6. **Готовый продукт, а не скрипт.** CLI одной командой, сайт и MCP-сервер для Claude Desktop и Cursor. Модель меняется в конфиге, при перегрузке API включается запасная модель, ответы кэшируются, этапы идут параллельно.

## Быстрый старт

### Вариант 1 — через сайт (без установки)
1. Откройте **https://clarifai-rv5l.onrender.com** и пролистайте баннер.
2. Перетащите документ с требованиями (PDF, DOCX, MD, TXT, HTML до 4 МБ).
3. Введите код доступа **`qwerty123`**. Можно вместо него указать свой ключ Gemini: он используется только для этой проверки и не сохраняется.
4. Нажмите **«Проверить»**. Через 1–3 минуты появятся вердикт, вкладка **«Документ и находки»** и кнопки скачивания отчёта в **PDF / Markdown / HTML**.

### Вариант 2 — локально, одной командой (Windows)
```bat
git clone https://github.com/Aqtanbi/clarifai.git
cd clarifai
py -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
```
Откройте `.env` и вставьте ключ в `GEMINI_API_KEY=` (как получить — ниже). Затем запустите проверку:
```bat
python main.py docs\requirements.pdf -o reports\report.md
```
Linux/macOS: `python3 -m venv .venv && source .venv/bin/activate`, далее те же команды (`cp .env.example .env`).

### Где отчёт
| Файл | Что это |
|---|---|
| `reports/report.md` | отчёт в Markdown |
| `reports/report.pdf` | тот же отчёт в PDF (кириллица, таблицы) |
| `reports/report_interactive.html` | **интерактивный отчёт «документ и находки»**, открывается в браузере без интернета |
| `reports/report.html` | HTML-версия отчёта |
| `reports/report.json` | машиночитаемый результат (требования, находки, расчёты, итог) |

### Ключ LLM и модель
1. Откройте https://aistudio.google.com/apikey, нажмите **Create API key** и скопируйте ключ. Бесплатного тарифа достаточно.
2. Вставьте его в `.env`: `GEMINI_API_KEY=...`. Файл `.env` в git не попадает. В репозитории лежит только пример `.env.example` без ключа.
3. **Модель команды — `gemini-3.5-flash-lite`** (Google AI Studio). На ней сформирован сдаваемый отчёт, она стоит по умолчанию. При перегрузке API запросы уходят на запасную `gemini-3.5-flash`. Модель, на которой выполнен прогон, записывается в паспорт отчёта. Список доступных моделей: `python main.py --list-models`.
4. Поддерживается и любой OpenAI-совместимый провайдер: `LLM_PROVIDER=openai` + `OPENAI_BASE_URL` (OpenAI, OpenRouter, Groq, локальная Ollama).

### Параметры CLI
```
python main.py <документ> [-o reports/report.md] [--full] [--fast] [--no-sim] [--no-critic] [--no-cache] [--model NAME]
```
`--full` — полный отчёт вместо краткого. `--fast` — без дополнительных проходов (сверка противоречий, вопросы разработчика). `--no-sim` — без проверки расчётом. `--no-cache` — без кэша ответов модели: по умолчанию повторный прогон того же документа берёт ответы из `.cache/`, работает воспроизводимо и не тратит лимиты.

## Как работает агент

```
документ (PDF/DOCX/MD/TXT/HTML)
  │  0. Парсинг        страницы, разделы, таблицы, номера строк (PyMuPDF, python-docx)
  │  1. Профиль        LLM: тип документа, предметная область, нумерация → чек-лист рисков под этот документ
  │  2. Нарезка        LLM: R-01…R-NN, ID из документа, дословная цитата, место
  ├──────────────── параллельно ────────────────┐
  │  3. Каждое требование   9 критериев ISO 29148 п. 5.2.5, пакетами
  │  4. Набор целиком       критерии 29148 п. 5.2.6 + IEEE 830 п. 4.3, трассируемость, термины
  │  5. Сверка противоречий расчёт КАЖДОГО критерия приёмки по тексту требований + пары связанных правил
  │  6. Проверка расчётом   LLM пишет модель правил на Python → песочница → сценарии и границы
  ├───────────────────────────────────────────────┘
  │  7. Вопросы разработчика   3–6 вопросов к каждому требованию: отвечает ли документ?
  │  8. Grounding       каждая цитата сверяется с документом; выдуманные — отбрасываются
  │  9. Склейка дублей  одна проблема, найденная разными этапами, — одна находка
  │ 10. Рецензент       LLM: снимает неверные находки, калибрует серьёзность, выносит итог
  ▼ 11. Отчёт          краткий / полный: MD + PDF + HTML + интерактивный HTML + JSON
```

**Критерии проверки** — все пункты стандартов, без упрощений:
- **ISO/IEC/IEEE 29148:2018 п. 5.2.5**, отдельное требование: необходимость, уместность уровня, однозначность, полнота, единичность, реализуемость, проверяемость, корректность, соответствие шаблону.
- **ISO/IEC/IEEE 29148:2018 п. 5.2.6**, набор требований: полнота, непротиворечивость, реализуемость, понятность, возможность валидации.
- **IEEE Std 830-1998 п. 4.3**: корректность, однозначность, полнота, непротиворечивость, ранжированность, проверяемость, модифицируемость, трассируемость.

### Состав отчёта (по ТЗ)
1. **Паспорт прогона:** документ, дата, модель, версия агента (git-тег/коммит), токены, время, профиль документа.
2. **Нарезка:** «ID в отчёте — ID в документе — тип — краткая формулировка — цитата».
3. **Проверка каждого требования:** матрица «требование × критерий» и карточки нарушений.
4. **Проверка всего набора:** критерии набора, трассируемость к критериям приёмки, неопределённые термины.
5. **Проверка расчётом:** сценарии модели и таблица пересчёта каждого критерия приёмки.
6. **Сводка:** число требований и нарушений, список критичных дефектов (непроверяемые, противоречивые, неполные) с местами.
7. **Итог:** можно ли начинать разработку и тестирование, что исправить в первую очередь.

По умолчанию формируется **краткий** отчёт: итог и главные дефекты на первой странице, мелкие замечания одной строкой. Полный отчёт со всеми карточками и приложениями включается флагом `--full` (на сайте — галочкой «Полный отчёт»).

### Соответствие ТЗ хакатона
| Требование ТЗ | Как выполнено |
|---|---|
| Документ на входе: PDF и другие форматы | PDF, DOCX, MD, TXT, HTML |
| Выделение требований, проверка каждого и набора | этапы 2–7, дозапрос, если модель пропустила требование |
| Критерии ISO 29148 п. 5.2.5–5.2.6, IEEE 830 п. 4.3 | все пункты, см. выше |
| Отчёт на русском: паспорт, нарезка, проверки, сводка, итог | разделы 1–7 |
| Каждое нарушение ссылается на место, без общих фраз | grounding цитат + место «раздел, страница, строка» |
| Любая LLM, модель указана в инструкции | Gemini / OpenAI-совместимые; модель команды — `gemini-3.5-flash-lite` |
| Запуск одной командой: путь к документу и к отчёту | `python main.py <документ> -o <отчёт>` |
| Секреты не в репозитории, `.env.example` в корне | ✓ |

## Сайт и MCP-сервер

**Сайт локально:** `uvicorn webapp:app` → http://127.0.0.1:8000.

**Защита серверного ключа:** без кода доступа (`ACCESS_CODE`) сервер не запускает проверку на своём ключе. Действует лимит прогонов в час с одного адреса (`RUNS_PER_HOUR`, по умолчанию 6). Свой ключ пользователя нигде не сохраняется.

**Развёртывание:**
- **Render.com** (используется для демо): New → Blueprint → этот репозиторий. Настройки берутся из `render.yaml`, Render запросит `GEMINI_API_KEY` и `ACCESS_CODE`.
- **Docker** (любой хостинг): `docker build -t clarifai .` и `docker run -p 8000:8000 -e GEMINI_API_KEY=... clarifai`.
- **Vercel:** конфигурация оставлена экспериментальной (`vercel.json`, `api/index.py`). Для долгих потоковых прогонов надёжнее Render или Docker.

**MCP-сервер** для Claude Desktop, Cursor, VS Code. Инструменты: `validate_requirements`, `extract_requirements`, `verify_quote` (без LLM), `list_criteria`, `validate_requirements_file`.
```json
{
  "mcpServers": {
    "clarifai": {
      "command": "C:\\path\\to\\clarifai\\.venv\\Scripts\\python.exe",
      "args": ["C:\\path\\to\\clarifai\\mcp_server.py"],
      "env": { "GEMINI_API_KEY": "ваш_ключ" }
    }
  }
}
```
Удалённо: Streamable HTTP по адресу `https://<сайт>/mcp/` (заголовок `Authorization: Bearer <MCP_TOKEN>`, если токен задан).

## Качество и тесты

```bat
python tests\test_pipeline.py
python eval\run_eval.py reports\report.json eval\gold.json
```
- `tests/test_pipeline.py` — офлайн-тест всего конвейера на моке LLM и нейтральном выдуманном документе, ключ не нужен.
- `eval/run_eval.py` — полнота (recall) находок по эталону дефектов, который команда размечает вручную. Нужен для сравнения версий промптов и моделей. Эталон в репозиторий не входит и агенту не передаётся.

| Версия конвейера (на `gemini-3.5-flash-lite`) | Полнота | Критичные |
|---|---|---|
| Базовый: нарезка + проверка требований и набора | 35% | 2/5 |
| + сверка противоречий с обязательным расчётом и «вопросы разработчика» | 56–71% | 4–5/5 |

## Структура
```
main.py               CLI (одна команда)
webapp.py             сайт + HTTP API + /mcp (FastAPI)
mcp_server.py         MCP-сервер (stdio)
validator/
  parsing.py          PDF/DOCX/MD/TXT/HTML → строки, страницы, разделы, таблицы
  prompts.py          промпты всех этапов (без подгонки под конкретный документ)
  pipeline.py         конвейер, параллельные этапы
  grounding.py        проверка цитат
  sandbox.py          песочница для исполняемой модели требований
  dedupe.py           склейка дублей
  criteria.py         критерии ISO 29148 / IEEE 830
  llm.py              провайдеры, JSON-схемы, повторы, запасная модель, кэш
  report/             краткий и полный отчёт, рендер MD / PDF / HTML / интерактивный HTML
web/                  страница сайта и интерактивный просмотрщик
render.yaml, Dockerfile, vercel.json   развёртывание
tests/, eval/         офлайн-тесты и оценка качества
```
